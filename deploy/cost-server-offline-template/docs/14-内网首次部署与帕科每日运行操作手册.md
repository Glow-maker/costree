# 内网首次部署与帕科每日运行操作手册

本手册适用于本离线包的首次内网部署、已有成本库升级和帕科每日全量快照同步。命令中的
`<...>` 都是现场占位符，必须替换后才能执行。密码只保存在部署机受控配置中，不要写进
脚本、截图或聊天记录。

## 0. 先填写现场信息

| 项目 | 现场值 |
|---|---|
| 部署包 ZIP SHA256 | 见交付说明 |
| 业务租户 ID | `<TENANT_ID>` |
| 成本库类型 | `PostgreSQL 9.2 / GaussDB(DWS) / PostgreSQL 14+` |
| 成本库是空库还是已有库 | `<EMPTY / EXISTING>` |
| SQL 客户端 | `<psql / gsql>` |
| 成本库备份文件 | `<BACKUP_PATH>` |
| DM8 平台库备份文件 | `<BACKUP_PATH>` |
| Nacos namespace/group | `<VALUE>` |
| Redis database和应用前缀 | `<VALUE>` |
| Nginx 管理端目录 | `<WEB_ROOT>` |
| 帕科源库和成本库是否可同库查询 | `<YES / NO>` |

没有确认租户 ID、数据库类型和空库/已有库状态前，不得执行数据库写入脚本。

## 1. 离线包完整性检查

将 ZIP 复制到内网部署机，先计算哈希并与交付值比较：

```powershell
Get-FileHash -Algorithm SHA256 .\cost-server-offline-package.zip
```

解压后进入包根目录：

```powershell
cd <解压目录>\cost-server-offline-package
pwsh -File .\tools\verify-package.ps1 -RequireFormal
Get-Content .\RELEASE-INFO.txt
```

成功标准：显示 `Package verification passed`，`releaseType=formal`，结构版本为 `20260820`。

**停止条件：** ZIP 哈希不同、验包失败或结构版本不一致时立即停止，不要从其他包补单个文件。

## 2. 停机与备份

1. 停止旧 `cost-server`。
2. 暂停帕科和其他写成本库的任务，确认没有同步批次运行。
3. 备份成本业务库，至少覆盖全部 `cost_*` 表和 `cost_schema_migration`。
4. 备份 DM8 `MQB` 中：
   - `SYSTEM_MENU`
   - `SYSTEM_ROLE`
   - `SYSTEM_ROLE_MENU`
   - `SYSTEM_USERS`
   - `SYSTEM_USER_ROLE`
   - `SYSTEM_NOTIFY_TEMPLATE`
5. 备份现有后端 JAR、前端站点目录和 Nginx 配置。
6. 记录升级前业务表行数、合同、到款、目标、账面和审定汇总。

**停止条件：** 没有可验证的数据库备份，或仍有同步任务运行时，不得继续。

## 3. 确认成本数据库类型

连接成本业务库执行：

```sql
SHOW server_version;
SHOW server_version_num;
SELECT version();
```

- 返回 `902xx`，或包含 `GaussDB/DWS`：只使用 `database/postgresql92`。
- 返回 `140000` 或更高：只使用 `database/postgresql`。
- 两套目录不能混用。本手册后续帕科路径按内网常用的 PostgreSQL 9.2/DWS 编写。

## 4. 成本业务库建库或升级

### 4.1 设置当前 PowerShell 会话参数

```powershell
$env:PGHOST='<成本库地址>'
$env:PGPORT='<端口>'
$env:PGUSER='<专用数据库账号>'
$env:PGPASSWORD='<在部署机安全输入>'
$env:PGDATABASE='<成本库名>'
cd .\database\postgresql92\02-upgrade-existing
```

DWS 建议增加：

```powershell
$env:COST_SQL_CLIENT='gsql'
```

### 4.2 二选一执行

空库：

```powershell
pwsh -File .\run-new-database.ps1
```

已有成本库：

```powershell
pwsh -File .\run-upgrade.ps1
```

不要同时执行两条命令，也不要只挑最后一个增量 SQL。已有库升级链必须完整运行 `10` 至
`15`，最后执行 `20-verify.sql`。

### 4.3 成功标准

```sql
SELECT version, description, installed_on, installed_by
FROM cost_schema_migration
ORDER BY installed_on DESC, version DESC;
```

- 存在 `20260820`。
- `20-verify.sql` 的全部错误计数为 `0`。
- `cost_subsystem_dict`、三张用户范围表以及三张预警闭环表存在。

**停止条件：** 出现第一条 `ERROR` 后立即停止。`current transaction is aborted` 通常只是后续
提示，应先定位前面的第一条错误；不要手工跳过增量或删除防重索引。

## 5. DM8 中台权限初始化（只执行一次）

DM8 只在首次部署或以后明确升级权限/通知模板时执行，不加入帕科每日任务。

1. 连接中台 DM8 平台库 `MQB`，不要连接成本 PostgreSQL/DWS 库。
2. 检查下列文件中的示例租户 `124`；若实际租户不同，在现场副本中统一替换为
   `<TENANT_ID>` 并复核。
3. 关闭客户端自动提交，确保失败可以回滚，禁止多人并发执行。
4. 严格串行执行：
   1. `database/platform/dm8/01-costree-role-menu-full-20260820.sql`
   2. `database/platform/dm8/02-cost-warning-notify-template-20260820.sql`
   3. `database/platform/dm8/03-check-cost-permissions-20260820.sql`
5. 检查器必须确认：4 个成本角色、21 个权限点、42 条角色权限映射完整，缺失、多余和
   用户角色冲突计数为 0。

脚本不会创建用户、修改密码或分配用户角色。这些操作稍后在业务中台页面完成。

**停止条件：** 任一 SQL 报错立即 `ROLLBACK`，修复后从第一份脚本重新执行。检查器没有
全部通过时不能放开用户登录。

## 6. 精确失效 Redis 权限缓存

DM8 SQL 直接写数据库，不会触发中台页面正常保存时的缓存清理。执行后必须：

1. 从 DM8 查询当前租户的4个成本角色 ID、21个权限菜单 ID及权限标识。
2. 连接 `system-server` 实际使用的 Redis database，先用 `SCAN` 找到完整键名：
   - `*role:<TENANT_ID>:<ROLE_ID>`
   - `*menu_role_ids:<TENANT_ID>:<MENU_ID>`
   - `*permission_menu_ids:<TENANT_ID>:<PERMISSION>`
   - `*notify_template:<TENANT_ID>:<TEMPLATE_CODE>`
3. 保存待删除键清单，只对确认后的完整键使用 `UNLINK`；Redis 不支持时才使用 `DEL`。
4. 四个模板编码：
   - `COST_WARNING_PENDING_DISPOSITION`
   - `COST_WARNING_FEEDBACK_SUBMITTED`
   - `COST_WARNING_RETURNED`
   - `COST_WARNING_CLOSED`

禁止使用 `FLUSHDB`、`FLUSHALL` 或 `*role*` 之类宽泛删除。详细查询与边界见
`database/platform/dm8/00-开始这里.md` 和 `docs/06-网关菜单权限.md`。

## 7. 部署并启动后端

回到部署包根目录：

```powershell
Copy-Item .\backend\config\cost-server.env.example .\backend\config\cost-server.env
notepad .\backend\config\cost-server.env
```

只在部署机填写成本库、Redis、Nacos等真实参数，然后启动：

```powershell
pwsh -File .\backend\bin\start-cost.ps1
pwsh -File .\backend\bin\status-cost.ps1
```

检查：

- `backend/logs` 无缺表、缺列、Redis或Nacos错误；
- Nacos 中 `cost-server` 实例健康；
- `http://<部署机>:38108/actuator/health` 返回健康；
- 网关 `/admin-api/cost/project/page?pageNo=1&pageSize=1` 可达。

## 8. 发布前端

Windows 示例：

```powershell
pwsh -File .\frontend\deploy-frontend.ps1 -WebRoot '<WEB_ROOT>'
```

必须发布整个 `frontend/dist`，不能只复制几个成本模块 JS。检查 Nginx 的
`/admin-api` 仍代理到现有网关，不直接代理 `cost-server`。发布后强制刷新浏览器。

## 9. 创建测试用户并配置成本范围

在业务中台“用户管理”中为测试账号分配且只分配一个成本业务角色：

| 角色 | 后续范围配置 |
|---|---|
| `cost_global_viewer` | 无需配置范围，只读全局 |
| `cost_research_department` | 必须选择一个领域 |
| `cost_project_office` | 必须选择项目 |
| `cost_unit_user` | 必须同时选择项目和管理单位，实际范围为二者交集 |

使用 `tenant_admin` 登录 `/cost/back/access-scope` 完成范围配置。所有账号退出并重新登录。
不同场所用户应位于同一业务租户，通过领域、项目和单位范围区分，不要关闭租户插件。

## 10. 初始化帕科中间表（只执行一次）

在成本 PostgreSQL 9.2/DWS 库执行：

`database/postgresql92/03-data-integration/snapshot-upsert/01-创建标准中间表.sql`

它创建 `cost_sync_stage` 和六张标准中间表。成功后不需要每天重跑。

## 11. 配置帕科每日工作流

完整说明见：

`database/postgresql92/03-data-integration/pako-daily/00-开始这里.md`

工作流必须严格串行、前一步失败即停止，禁止两个批次并发。每日节点固定为：

1. `snapshot-upsert/02-只清空中间表.sql`
2. 装载六类源全量快照，二选一：
   - 同库可查询：现场只修改并执行
     `pako-daily/01-同库全量装载-现场只改此文件.sql`；
   - 跨库：帕科写入六张 `cost_sync_stage.stg_*` 表，再执行
     `pako-daily/02-跨库装载完成标记.sql`。
3. `snapshot-upsert/04-导入前检查.sql`
4. `snapshot-upsert/05-业务表幂等同步.sql`
5. `snapshot-upsert/06-重算工作令账面.sql`
6. `snapshot-upsert/07-同步后验收.sql`
7. 可选保存 `snapshot-upsert/08-缺失数据差异清单.sql` 输出。

帕科写入节点只能写 `cost_sync_stage.stg_*`，不能直接写 `costree_mvp`。标准同步不会清空
业务表，不会覆盖手工填报、流程状态、分系统字典和预警闭环历史。

## 12. 首批同步验收

第一批先限制为少量可人工对账的真实项目。第 6 个节点成功后检查：

```sql
SELECT id, tenant_id, batch_code, source_tag, load_status, loaded_at, synced_at, remark
FROM cost_sync_stage.sync_control
WHERE id = 1;
```

`load_status` 必须为 `SUCCESS`。随后：

1. 核对六张中间表行数与源系统一致。
2. 核对项目、单位、工作令和账面金额。
3. 确认项目办、研制单位填报字段和流程状态未改变。
4. 用完全相同的源快照再执行一次，业务行数和金额不得翻倍。
5. 修改源系统一条合同或到款，再同步，现有业务行应更新为新值。
6. 源快照缺少旧记录时只进入差异清单，不应删除业务历史。

## 13. 账号与页面验收

至少使用 `tenant_admin`、全局查看、科研部、项目办、研制单位五类真实账号验证：

- 默认入口、菜单和直接 URL；
- 项目、单位、工作令列表和详情；
- 领域、项目、单位越权应拒绝；
- 填报、提交、审批和导出权限；
- 预警推送、研制单位反馈、项目办退回/闭环及站内信；
- 账面组成、成本树和单位页汇总。

编译、静态验包和模拟账号不能替代这一步。

## 14. 回滚和日常故障处理

- 数据库升级失败：保持服务和同步任务停止，按数据库备份恢复，不要在半升级状态上线。
- DM8 初始化失败：事务回滚后修复第一条错误，从第一份脚本重跑。
- 帕科批次失败：停止后续节点，修复映射后从“只清空中间表”开始完整重跑。
- 后端启动失败：先查 `backend/logs`，不要只根据最后一条 Spring 异常判断原因。
- 前端异常：确认发布了完整 `frontend/dist`，清浏览器缓存，并检查 `/admin-api` 网关代理。
- 任何回滚都应保留失败日志、批次号、SQL输出和备份路径，便于审计。

## 15. 建议现场执行节奏

为降低风险，分四个确认点推进：

1. **确认点 A：** 完成包验收、数据库类型识别和备份，把非敏感输出交给实施负责人确认。
2. **确认点 B：** 完成成本库升级和 DM8 检查器，所有错误计数为 0。
3. **确认点 C：** 后端、前端、网关和五类账号权限验收通过。
4. **确认点 D：** 两批相同源快照幂等通过，再开启帕科每日调度。

不要跨过失败的确认点继续上线。
