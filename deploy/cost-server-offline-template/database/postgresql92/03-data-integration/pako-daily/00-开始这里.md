# 帕科每日全量快照更新：最简执行说明

本目录用于在帕科平台建立每天串行执行的成本数据更新工作流。它不是
`../minimal/` 的替代品：`minimal/` 只适合空业务表的首次插入，不能每天执行。

本流程的固定口径是：**外部源每天全量装入六张中间表，只清中间表；成本业务表按
业务键 UPDATE + INSERT，不清空、不删除，不覆盖项目办、研制单位填报、流程状态、
预警任务、接收人或处置日志。**

## 一、首次部署一次性执行

### 1. 成本 PostgreSQL 9.2 / GaussDB(DWS) 业务库

按以下顺序执行一次：

1. 按 `../../02-upgrade-existing/README.md` 运行完整已有库升级链至 `20260820`，并执行
   `20-verify.sql`；不要拆跳其中的 `10`—`15` 增量。
2. 执行 `../snapshot-upsert/01-创建标准中间表.sql`。

上述结构升级和中间表创建成功后不需要每天重跑。

### 2. 达梦中台平台库 MQB（DM8_ONCE）

DM8 中台更新是首次部署的一次性步骤，不得放进帕科每日工作流：

1. `../../../platform/dm8/01-costree-role-menu-full-20260820.sql`
2. `../../../platform/dm8/02-cost-warning-notify-template-20260820.sql`
3. `../../../platform/dm8/03-check-cost-permissions-20260820.sql`
4. 按 `../../../platform/dm8/00-开始这里.md` 精确失效相关 Redis 权限和通知模板缓存；禁止
   `FLUSHDB`、`FLUSHALL`。
5. 在中台页面创建用户并分配角色，在成本授权页配置领域、项目或管理单位，然后重新登录。

以后只有角色权限点、角色映射或站内信模板版本发生变化时，才按对应升级说明重新执行
DM8 脚本和精确清缓存；正常每日数据更新不访问 DM8。

## 二、现场只需要改哪个文件

如果源表与成本库可在同一个 PostgreSQL/DWS 会话中查询，只编辑：

`01-同库全量装载-现场只改此文件.sql`

只替换六段 `SELECT ... FROM` 中的源 schema、源表和源字段映射。不要改目标中间表列、
事务、空快照保护和 `READY` 标记。

如果源库与成本库不能跨库 SQL 查询，则不要执行该文件。由帕科的数据抽取/写入节点把
六类全量数据写入下表，再执行 `02-跨库装载完成标记.sql`：

| 顺序 | 目标表 | 业务粒度/关键字段 |
|---|---|---|
| 1 | `cost_sync_stage.stg_unit_dict` | 实际核算单位编码 |
| 2 | `cost_sync_stage.stg_model_node` | 型号树节点编码 |
| 3 | `cost_sync_stage.stg_project` | 项目编号 |
| 4 | `cost_sync_stage.stg_unit_amount` | 项目编号 + 实际核算单位编码 |
| 5 | `cost_sync_stage.stg_work_order` | 项目编号 + 实际核算单位编码 + 工作令号 |
| 6 | `cost_sync_stage.stg_ledger_detail` | 源账面明细唯一 ID |

帕科写入节点只能写 `cost_sync_stage.stg_*`，不能直接写 `costree_mvp` 业务表。

## 三、帕科每日节点（PAKO_DAILY）

工作流必须设置为**严格串行、前一步失败即停止（STOP_ON_FAILURE）**，禁止多个批次并发。

1. 执行 `../snapshot-upsert/02-只清空中间表.sql`。
2. 装载本批六类源全量快照，二选一：
   - 同库：执行 `01-同库全量装载-现场只改此文件.sql`；
   - 跨库：依次写入六张中间表，再执行 `02-跨库装载完成标记.sql`。
3. 执行 `../snapshot-upsert/04-导入前检查.sql`。
4. 执行 `../snapshot-upsert/05-业务表幂等同步.sql`。
5. 执行 `../snapshot-upsert/06-重算工作令账面.sql`。
6. 执行 `../snapshot-upsert/07-同步后验收.sql`。
7. 可选执行 `../snapshot-upsert/08-缺失数据差异清单.sql`，保存为审计结果。

只有第 6 步成功、`cost_sync_stage.sync_control.load_status` 为 `SUCCESS`，整批才算成功。
第 7 步只输出差异，不删除本次源快照中缺少的历史业务行。

## 四、每天会更新和不会更新的内容

会随外部源最新快照更新：

- 项目和型号树的外部主数据字段；
- 单位金额中的合同、到款及外部溯源字段；
- 工作令的源主键、项目、实际核算单位、编号、名称和停用状态；
- 账面明细全部外部源字段，以及由借方明细重算的工作令账面金额。

不会被每日流程覆盖：

- 项目办填报、研制单位填报、目标和审定；
- 阶段、分系统、工作令简称、配套数、纵向分工、负责人和流程状态；
- `cost_project_basic`；
- `cost_subsystem_dict`；
- `cost_warning_record`、`cost_warning_receiver`、`cost_warning_action_log`。

因此外部系统把某项目合同金额修正后，下一次全量快照会通过 UPDATE 更新现有业务行，
不会因为“记录已经存在”而跳过；手工填报和预警闭环数据仍保持不变。

## 五、失败与重跑

- 任一节点报错立即停止，不要继续执行后续节点。
- 修正源字段映射后，从第 1 步重新运行完整批次；不要从业务同步中间步骤接着跑。
- 同一份源快照完整执行两次，业务行数和金额不得翻倍。
- 首次上线和映射变化后，必须在真实库核对六张中间表行数、业务表金额、手工字段摘要和
  `08-缺失数据差异清单.sql`。
- `manual-preservation/` 只用于经批准的旧清库恢复或灾备演练，不得加入帕科定时任务。
