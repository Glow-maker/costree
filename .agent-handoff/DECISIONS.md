# 已定决策

- DEC-001: 成本库作为业务中台内嵌模块建设，不做独立系统。
  时间：2026-06-12 00:15:17 +0800
  原因：复用业务中台登录、租户、权限、菜单、组织、消息、导入导出和网关能力，降低集成和运维成本。
- DEC-002: Figma/React 原型只作为页面和交互参考，最终按 Vue3 + Yudao 后端规范重写。
  时间：2026-06-12 00:15:17 +0800
  原因：业务中台前端技术栈为 Vue3，直接嵌 React 原型会增加集成和维护风险。
- DEC-003: 后端采用 yudao-module-cost + cost-server 独立服务接入业务中台。
  时间：2026-06-12 00:15:17 +0800
  原因：便于成本库独立启动、注册到 Nacos，并通过网关按 /admin-api/cost/** 访问。
- DEC-004: 成本库默认使用业务中台真实登录态，VITE_COST_MOCK_LOGIN 只用于独立调试。
  时间：2026-06-12 00:15:17 +0800
  原因：避免前端代理注入 login-user 覆盖真实用户、角色、租户和数据权限，保证权限验收可信。
- DEC-005: 涉及真实数据量的列表和明细默认后端分页，禁止先查全量再手动分页。
  时间：2026-06-12 00:15:17 +0800
  原因：待分配池、预警中心、目录工作令等页面未来数据量可能很大，需要从设计上避免加载慢和内存压力。
- DEC-006: 真实内网库不得执行 seed-mvp.sql。
  时间：2026-06-12 00:15:17 +0800
  原因：seed-mvp.sql 只用于外网测试库构造样本，真实库执行会覆盖或污染内网真实数据。
- DEC-007: 长期项目按活文档机制维护：note 作为项目事实源，.agent-handoff 作为快速恢复层。
  时间：2026-06-12 01:51:08 +0800
  原因：成本库项目会持续多轮开发，新会话和后续维护者不能依赖聊天记录。后续开发前必须先读文档中心，开发后做状态更新和经验沉淀；文档保持短、准、可执行，避免复制散落。
- DEC-008: 成本库默认只按模块边界开发，修改其他模块必须先通知并文档留痕。
  时间：2026-06-12 19:07:05 +0800
  原因：成本库嵌入既有业务中台，随意修改非成本模块会增加回归风险和责任边界不清。后续如确需触碰其他模块，必须说明原因、影响范围、是否临时和回归方式。
- DEC-009: 成本服务离线包不提交到 root Git 仓库，只保留本地目录和 zip 作为部署介质。
  时间：2026-06-18 02:23:27 +0800
  原因：离线包包含 120MB+ 的可执行 jar/zip，大二进制不适合进入源码仓库；root 仓库继续只承载项目文档、交接状态和忽略规则。
- DEC-010: PostgreSQL seed 只用于测试验证环境，真实内网库只执行 DDL 后导入真实数据。
  时间：2026-06-18 02:23:27 +0800
  原因：测试 seed 用于复现外网样例和页面路径，正式环境执行会污染真实数据；真实数据导入需按内网租户、组织和数据权限写入。
- DEC-011: 成本库当前操作指南和协作文档默认使用 <costree-root>、<frontend-root>、<backend-root> 与相对路径，不写死本机盘符。
  时间：2026-06-18 02:37:52 +0800
  原因：文档需要在内网、陵台计算机和不同开发机之间复用；写死 H:、D: 或个人用户目录会导致接管 prompt、部署命令和文件引用不可执行。
- DEC-012: 内网三张原表不直接作为成本库页面业务表使用，先映射到成本库业务表。
  时间：2026-06-22 00:04:53 +0800
  原因：原表字段全是字符串且口径来自源系统，缺少成本库页面需要的目标成本、阶段、分系统、展示树节点类型等字段；直接使用会让页面逻辑和源表结构强耦合。
- DEC-013: cost_model_node 和 cost_project 继续分开维护。
  时间：2026-06-22 00:04:53 +0800
  原因：cost_model_node 负责左侧领域-系列-型号展示树，cost_project 负责项目卡片、项目详情、成本树和工作令关联；这样内网项目树层级变化时不会直接破坏业务项目锚点。
- DEC-014: 账面成本优先由 cost_work_order_ledger_detail 聚合，目标成本和阶段等业务字段由 cost_work_order 维护。
  时间：2026-06-22 00:04:53 +0800
  原因：账面明细是凭证明细来源，但不包含目标成本、阶段、分系统等填报字段；预警需要账面成本和目标成本同时存在。
- DEC-015: 项目办填报的是否产品附件/发射车字段直接存中文值，不新增独立字典表。
  时间：2026-06-26 10:24:02 +0800
  原因：当前 /cost/collect 的用户、获取方式等字典也采用前端固定下拉和中文值保存；本字段值域小且稳定，先按同一方式实现，降低实施复杂度。
- DEC-016: 承研单位使用 cost_unit_dict 作为下拉来源。
  时间：2026-06-26 10:24:02 +0800
  原因：承研单位属于单位口径数据，直接手输容易产生名称不一致；用成本库单位字典可与后续单位成本、工作令和权限口径保持一致。
- DEC-017: 多单位树详情默认采用单位矩阵视图，保留原树图作为可选视图。
  时间：2026-06-26 10:24:02 +0800
  原因：当单位超过 7 家时树图横向滚动成本高，矩阵更适合扫读和点击穿透；少单位场景仍保留树状连线展示。
- DEC-018: 院内单位展示和预警以管理单位简称为口径，实际核算单位仅在穿透层保留。
  时间：2026-07-21 19:36:08 +0800
  原因：多个核算单位可能同属电子所等管理单位，管理层展示需要合并，但账面明细和工作令查询仍必须保留实际单位以避免错误合并。
- DEC-019: 管理单位分类由 cost_unit_dict.manage_unit_group 显式维护。
  时间：2026-07-21 19:36:08 +0800
  原因：总体所、总装所、专业所、基础所的业务分类不能仅靠名称猜测；显式字典字段便于内网同步和后续维护，缺失值进入未分类。
- DEC-020: 单位使用率排名只纳入院内管理单位，使用率按账面成本除以目标成本计算。
  时间：2026-07-21 19:36:08 +0800
  原因：院外单位当前没有权威账面成本口径，纳入排名会产生无意义的 0% 或错误比较。
- DEC-021: 一条工作令只保留一条跨年度逻辑记录，年度属于账面明细而不属于工作令主数据。
  时间：2026-07-22 01:13:16 +0800
  原因：同编号工作令跨年度业务身份不变，按年度拆分主数据会造成重复展示和固定金额冲突；年度账面仍可通过明细追溯。
- DEC-022: 工作令合同、到款、目标和审定仅用于工作令层核对，不参与项目和单位金额汇总。
  时间：2026-07-22 01:13:16 +0800
  原因：项目单位金额继续以预分预控同步到 cost_unit_cost_detail 的数据为权威来源，避免工作令人工填报反向污染正式汇总。
- DEC-023: 工作令账面成本是全部年度借方明细的可重建快照，禁止人工维护。
  时间：2026-07-22 01:13:16 +0800
  原因：cost_work_order_ledger_detail 是账面唯一事实源，快照仅用于查询性能和页面展示，贷方不进入成本统计。
- DEC-024: 阶段筛选采用工作令阶段集合完整包含规则，而不是任一阶段命中。
  时间：2026-07-22 04:17:57 +0800
  原因：C/Z 表示组合阶段；只选择 C 或 Z 时不应将 C/Z 工作令误计入金额、数量和组成统计。
- DEC-025: 工作令组成提供原始借方明细导出和按工作令汇总的八项组成导出两种口径。
  时间：2026-07-22 04:17:57 +0800
  原因：原始凭证明细用于财务核对，工作令一行的八项金额与占比用于业务汇报，两者不能相互替代。
- DEC-026: 内网数据库升级采用可校验的 PostgreSQL 三段式脚本包。
  时间：2026-07-22 04:17:57 +0800
  原因：先检查冲突、再迁移、最后验证可避免只换 jar 导致缺列、重复业务键或金额口径错误。
- DEC-027: 预分预控同步只负责项目单位合同金额和到款金额。
  时间：2026-07-28 21:39:16 +0800
  原因：目标成本和审定金额改由项目办逐单位维护，正式同步重跑必须保留人工维护值。
- DEC-028: 项目办单位金额继续复用 cost_unit_cost_detail，不新增平行金额表。
  时间：2026-07-28 21:39:16 +0800
  原因：该表已经是项目编码加单位名称的权威单位金额粒度，复用可避免首页、成本树和采集页出现两套口径。
- DEC-029: 20260728 既有库升级必须在 20260722 升级后追加执行独立 11 脚本。
  时间：2026-07-28 21:39:16 +0800
  原因：保持既有部署顺序可追溯，同时让 PostgreSQL 9.2/GaussDB 现场升级不依赖不兼容的 IF NOT EXISTS 列语法。
- DEC-030: 成本权限采用中台身份权限与成本数据范围双库分治。
  时间：2026-08-17 15:01:32 +0800
  原因：达梦 MQB.SYSTEM_* 已承载登录用户、角色和接口权限，成本 PostgreSQL/GaussDB 更适合只保存项目与管理单位授权；cost-server 通过中台 API 获取身份后再叠加成本范围，避免跨库直连和把业务授权塞入部门权限。
- DEC-031: 外部源常规同步采用全量快照进入中间表后按业务键 UPDATE+INSERT。
  时间：2026-08-17 15:01:32 +0800
  原因：每批只清空 cost_sync_stage，中间层完成校验后幂等更新业务表；源快照缺失不自动删除，防止抽取不完整误删项目办和研制单位人工维护数据。
- DEC-032: 当前系列改动全部确认前不重复构建前端或完整离线包。
  时间：2026-08-17 15:01:32 +0800
  原因：前后端和数据库脚本仍在连续调整，反复生产构建和打包会浪费时间并产生多个不可识别版本；完成验证与用户确认后只生成一次正式包。
- DEC-033: 普通成本角色的若依通用数据范围固定为 SELF=5。
  时间：2026-08-17 15:51:21 +0800
  原因：成本全量、项目和管理单位范围由 CostAccessScopeService 与 cost_user_*_scope 独立控制；若把成本角色设为通用 ALL=1，会连带扩大用户在其他中台模块的部门数据权限。
- DEC-034: 项目和单位授权表采用租户内物理替换。
  时间：2026-08-17 15:51:21 +0800
  原因：现有唯一键不含逻辑删除状态，逻辑删除后重插相同授权会在 MySQL/PostgreSQL 冲突；授权关系不承担历史审计职责，事务内物理删除再插入是当前最小且可重复保存的方案。
- DEC-035: 通用保存接口只能处理草稿类状态，状态迁移由专用命令控制。
  时间：2026-08-17 15:51:21 +0800
  原因：客户端可写 status 会绕过提交与审批权限；创建强制 DRAFT，更新只接受空、UNFILLED、DRAFT、REJECTED，并由 submit/approve/reject 接口执行后续状态迁移。
- DEC-036: tenant_admin 作为共享业务租户内的成本授权管理员。
  时间：2026-08-18 02:31:55 +0800
  原因：不同场所使用同一 tenant_id，并由成本项目和管理单位范围区分；保留 tenant_admin 可确保有人维护授权，同时不需要关闭全局租户插件或把现场用户建成不同租户。
- DEC-037: cost_unit_user 的有效范围采用项目集合与管理单位集合的交集。
  时间：2026-08-18 02:31:55 +0800
  原因：研制单位用户需要显式选择项目和单位以避免新增同单位项目时自动扩权；两张既有 scope 表可表达 P×U 范围，无需新增关联表。
- DEC-038: 非成本角色登录业务中台时不加载成本权限档案。
  时间：2026-08-18 02:31:55 +0800
  原因：成本 profile 只用于成本角色默认落地与菜单裁剪；在所有账号登录时同步调用会把 cost-server 的延迟或故障传播到其他中台模块。
- DEC-039: snapshot-upsert 明确采用分阶段提交状态机而非跨文件原子事务。
  时间：2026-08-18 02:31:55 +0800
  原因：现有执行器逐文件启动 psql，无法保证跨文件 ROLLBACK；用 BUSINESS_SYNCED、RECALCULATED、SUCCESS 区分阶段，并只在最终验收脚本设置 SUCCESS，避免假成功。
