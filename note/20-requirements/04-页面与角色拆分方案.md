# 页面与角色拆分方案

状态：初稿

## 1. 背景

原型阶段使用 `Table 2`、`Table 3` 作为页面和数据表编号，便于和业务原型沟通。后续进入中台开发后，不应继续把 `Table 2`、`Table 3` 作为最终页面名、接口名、权限名或数据库表名。

开发口径调整为：

| 原型编号 | 业务名称 | 主要开放对象 | 开发命名建议 |
|---|---|---|---|
| `Table 1` | 主业项目锚定信息 | 所有授权角色只读 | `project-anchor` / `cost_project` |
| `Table 2` | 项目基本情况 | 项目办 | `project-basic` / `cost_project_basic` |
| `Table 3` | 工作令基础信息 | 研制单位 | `work-order` / `cost_work_order` |

## 2. 页面拆分原则

- 成本项目列表作为共同入口，所有授权角色都从这里进入项目上下文。
- 主业项目锚定信息作为公共只读区，不单独作为人工维护页面。
- 项目办进入“项目基本情况维护”页面，默认只看到项目办需要维护的字段和按钮。
- 研制单位进入“工作令基础信息维护”页面，默认只看到研制单位需要维护的字段和按钮。
- 管理员可同时进入两类维护页面，用于外网测试、初始化数据和排查。
- 是否允许项目办只读查看工作令、研制单位只读查看项目基本情况，需要业务确认【需确认】。

## 3. MVP 页面清单

| 页面 | MVP | 主要用户 | 说明 |
|---|---|---|---|
| 成本项目列表 | 是 | 管理员、项目办、研制单位、审核人员 | 查询主业项目，进入对应维护页 |
| 项目基本情况维护 | 是 | 项目办、管理员 | 原型 `Table 2`，包含查询、CRUD、保存草稿、提交、导入导出 |
| 工作令基础信息维护 | 是 | 研制单位、管理员 | 原型 `Table 3`，包含查询、CRUD、保存草稿、提交、导入导出 |
| 预警记录列表 | 简版 | 管理员、管理层【需确认】 | 阈值暂定 10%，全部推送，仅用于外网测试闭环 |
| 驾驶舱 | 否 | 管理层 | 二阶段 |
| 成本树详情 | 否 | 项目办、研制单位、管理层 | 二阶段 |
| 型号对比 | 否 | 管理层、项目办【需确认】 | 二阶段 |

## 4. 建议路由草案

| 页面 | 前端路由草案 | 组件路径草案 |
|---|---|---|
| 成本项目列表 | `/cost/project` | `cost/project/index` |
| 项目基本情况维护 | `/cost/project-basic` 或 `/cost/project/basic/:projectId`【需确认】 | `cost/project-basic/index` |
| 工作令基础信息维护 | `/cost/work-order` 或 `/cost/project/work-order/:projectId`【需确认】 | `cost/work-order/index` |
| 预警记录列表 | `/cost/warning` | `cost/warning/index` |

推荐 MVP 使用“列表页 + query 参数/路由参数进入维护页”的方式，不把两个维护区长期塞进一个复杂详情页。这样更符合后续按角色开放的目标。

## 5. 权限控制口径

| 控制层 | MVP 做法 |
|---|---|
| 菜单权限 | 项目办只配项目基本情况菜单，研制单位只配工作令基础信息菜单【需确认最终菜单是否分开】 |
| 按钮权限 | 新增、编辑、删除、导入、导出、提交分别配置 `cost:*:*` 权限 |
| 接口权限 | Controller 使用 `@PreAuthorize("@ss.hasPermission('cost:...')")` |
| 数据权限 | 项目办按授权项目；研制单位按本单位或授权项目【需确认】 |
| 字段权限 | MVP 暂不做字段级权限，只通过页面和接口拆分降低复杂度 |

## 6. 需要确认

- 项目办是否可以只读查看工作令基础信息。
- 研制单位是否可以只读查看项目基本情况。
- 审核人员是在两个维护页面内审核，还是单独有审核列表。
- 保存草稿和提交状态是项目级、项目基本情况记录级，还是工作令记录级。
- 内网真实角色名称是否就是“项目办”和“研制单位”，还是需要映射到现有组织/岗位/角色编码。
