# 成本库嵌入数据中台的可行性评估与项目蓝图

## 总体判断

这个任务**可以接**，但前提不是“让 AI 一把梭把一个完整生产系统写出来”，而是把它当成一个**有现成中台能力可复用的业务模块建设**来做：你的原型已经把页面结构、交互路径和主要业务对象讲清楚了；数据中台已经提供了登录、菜单路由、权限、组织、导入导出、消息、定时任务和数据权限这几块最难的基础设施；真正需要你攻克的，是**业务规则确认、数据模型设计、模块嵌入方式、以及用 AI 按现有代码风格“仿照开发”**。从仓库事实看，这个判断是成立的：`costree` 是一个 React/Vite 原型项目；`data_platform_frontend` 是 Vue3/Vite/Element Plus/Pinia/Vue Router 的中台前端；`data_platform_backend` 是基于 Yudao 体系的 Spring Boot 2.7、多模块 Java 8 后端，已经启用了 system、infra、bpm、finance、digital、center 等模块。fileciteturn105file0L3-L3 fileciteturn106file0L3-L3 fileciteturn52file0L3-L3

我给你的直白判断是：**你能做，但不能靠“不会 Java 也没关系，AI 会全写”这种心态做**。行业里做得好的人，一般会把这种项目拆成“原型转规格”“规格转接口”“接口转页面”“页面转联调”四段，每一段都用 AI 提速，但关键边界——尤其是公式、权限、导入模板、审批/预警规则——必须由人拍板。你的优势是原型已经被业务认可，需求入口是清楚的；你的风险是后端、权限、数据规则这三块还没有经验。也正因为如此，这个项目最适合用**阶段化的 vibe coding**：先做壳子、再做列表、再做明细、再做导入、最后做预警，而不是一开始就冲完整驾驶舱。这个建议并不是空泛经验，而是基于你当前中台已经具备的复用能力：前端权限和菜单是现成的，按钮权限有 `v-hasPermi`，用户信息里直接有 `permissions`、`roles` 和 `menus`，请求层已经封装了 `download` 和 `upload`；后端已经有消息、预警配置、Excel 导入导出、XXL-Job/Spring 定时任务、BPM 模块和数据权限注解。fileciteturn83file0L3-L3 fileciteturn108file0L3-L3 fileciteturn26file0L3-L3 fileciteturn27file0L3-L3 fileciteturn112file0L3-L3 fileciteturn65file0L3-L3 fileciteturn66file0L3-L3 fileciteturn68file0L3-L3 fileciteturn75file0L3-L3 fileciteturn110file0L3-L3

## 我对这个成本库项目的业务理解

从原型路由看，这个项目不是一个单页表单，而是一套比较完整的业务模块：根页面下有总体展示、领域/型号选择、成本树详情、型号对比、预警看板、数据采集列表、项目详情/填报页这几类页面。具体路由包括 `/`、`/select/:domain`、`/tree/:id`、`/compare`、`/warning`、`/data-collection`、`/project/:id`。fileciteturn104file0L3-L3

总体展示页的意思很清楚：它不是“数据录入入口”，而是**成本驾驶舱首页**。原型中按四个领域展示六边形指标卡和成本组成饼图，每个领域都围绕“合同金额、到款率、到款金额、账面金额、执行率、目标金额”六项指标来展开，并且支持点击进入领域下的型号选择页；页面底部还提供“进入数据采集”的快捷入口。也就是说，这个首页本质上是“看板 + 导航中心”。fileciteturn86file0L3-L3 fileciteturn87file0L3-L3

领域/型号选择页承担的是**“领域—系列/类别—批次/项目—阶段”多维筛选与项目入口聚合**的作用。原型里除了快速检索，还支持收藏过滤、领域筛选、系列筛选、批次筛选、阶段筛选，并且在顶部放了“超支预警”“型号对比”“数据导入”三个全局入口。筛选结果是一个项目卡片列表，点击进入详情。这说明你的“三级树”在业务上并不一定要死板做成传统左树右表，也可以像原型这样做成“树形思维导图式筛选器 + 结果卡片”；落到 Vue 实现时，可以转成更适合中台风格的“左树右列表”，但业务语义要保留：**领域、系列、批次、阶段是核心维度**。fileciteturn89file0L3-L3 fileciteturn90file0L3-L3

数据采集列表页是典型的中台业务列表：查询条件包括主业项目编号、主业项目名称、所属领域、审批状态；列表字段包括主业项目编号、名称、所属领域、所属类别、项目办填报状态、研制单位填报状态、审批状态、最后更新时间；操作是查看/进入填报。这个页面已经把系统的核心协作关系暴露出来了：**至少有“项目办”和“研制单位”两类填报主体**，而且审批状态是独立维度。fileciteturn88file0L3-L3

## 核心角色与页面清单

从原型文案和操作路径推断，至少有四类核心角色。第一类是**管理层/项目统筹视角**，主要看总体展示、型号对比、预警看板，不一定直接编辑数据；第二类是**项目办/总体单位**，会进入数据采集列表和项目详情，维护 Table 2、发起提交、参与初审；第三类是**研制单位**，会在项目详情里维护 Table 3，也会消费成本树详情；第四类是**财务/科研/型号两总等审批或会签角色**，原型里审批流依次出现“项目办初审—财务部会签—科研部会签—型号两总审批”。这里面第二、三、四类带有明显业务文案证据；第一类是基于首页、预警、对比页的典型使用方式做的合理推断。fileciteturn88file0L3-L3 fileciteturn91file0L3-L3 fileciteturn93file0L3-L3 fileciteturn94file0L3-L3 fileciteturn95file0L3-L3

如果把页面清单按最终中台模块来整理，我建议这样理解。第一组是**展示层**：总体展示页、型号对比页、超支预警页、成本树详情页。第二组是**入口与导航层**：领域/系列/型号筛选页、数据采集项目列表页。第三组是**主业务维护层**：项目详情页，包括锚定项目区、Table 2、Table 3。第四组是**弹窗/抽屉层**：Table 2 新增编辑抽屉、Table 3 新增编辑抽屉、批量导入弹窗、审批流程抽屉、版本对比【需确认原型仅露出入口】。这些页面基本已经由 `costree` 路由和各个页面组件一一对应。fileciteturn104file0L3-L3 fileciteturn89file0L3-L3 fileciteturn88file0L3-L3 fileciteturn91file0L3-L3 fileciteturn92file0L3-L3 fileciteturn93file0L3-L3

## 为什么最终应该选 Vue3 而不是继续沿用 React

这个问题其实不需要纠结太久：**最终生产代码应该选 Vue3，React 原型只保留为“视觉和交互参考”**。原因非常硬。`costree` 明确是 Vite + React Router + Radix UI + Recharts 的原型项目；而数据中台前端明确是 Vue3、Vite、Element Plus、Pinia、Vue Router，并且已经有成熟的请求封装、权限、用户缓存和动态菜单机制。把 React 原型直接塞进现有中台，短期也许能跑，长期一定会引入双技术栈维护成本。fileciteturn105file0L3-L3 fileciteturn106file0L3-L3 fileciteturn104file0L3-L3

更关键的是，这个中台不是“只有个空壳 Vue 项目”，而是已经形成了完整的管理后台工作流。用户信息里直接缓存 `permissions`、`roles` 和 `menus`；权限路由是从 `ROLE_ROUTERS` 动态生成的；按钮权限通过 `v-hasPermi` 指令控制；请求层已经内置了 token、tenant、blob 下载和 multipart 上传；类似导入场景已经有现成的弹窗上传模式。你要做的不是搭一套新前端框架，而是把成本库页面塞进这个生态里。fileciteturn83file0L3-L3 fileciteturn108file0L3-L3 fileciteturn27file0L3-L3 fileciteturn111file0L3-L3 fileciteturn112file0L3-L3 fileciteturn102file0L3-L3

确实，前端 `package.json` 里有 `qiankun` 依赖，理论上可以做微前端，把 React 原型作为子应用挂进去。可我不建议你这样做。原因不是“不能做”，而是**不值得**：成本库不是一个边界特别独立、未来会长期独立演进的系统，它高度依赖现有中台的菜单、权限、字典、组织、导入导出、消息和接口规范。为一个这样的模块同时维护 React 子应用和 Vue 主应用，会把你从“完成业务建设”拖进“前端架构维护”的坑里。对你当前这个挑战来说，正确取舍是：**React 代码只当规格说明书，Vue3 才是交付形态**。fileciteturn106file0L3-L3 fileciteturn83file0L3-L3 fileciteturn108file0L3-L3 fileciteturn111file0L3-L3

## 数据对象、数据表初稿与接口清单初稿

从原型反推，成本库至少涉及八类数据对象。第一类是**维度主数据**：领域、系列/类别、型号/批次、阶段；第二类是**主业项目锚定对象**，即来自外部系统或主数据系统的项目基础信息；第三类是**项目基本情况表**，对应原型里的 Table 2；第四类是**工作令基础信息表**，对应 Table 3；第五类是**驾驶舱统计对象**，用于首页六边形指标与成本组成饼图；第六类是**导入批次与导入结果对象**；第七类是**预警记录对象**；第八类是**审批/版本对象**，如果你最终需要保留版本对比和审批痕迹。这个拆法是直接从页面结构反推出来的，不是拍脑袋扩表。fileciteturn86file0L3-L3 fileciteturn87file0L3-L3 fileciteturn91file0L3-L3 fileciteturn92file0L3-L3 fileciteturn93file0L3-L3 fileciteturn94file0L3-L3

据此，我建议的数据表初稿如下。  
`cost_model_node`：领域/系列/型号/批次树节点表，【如果中台已有对应主数据则不新建，仅做关联】。  
`cost_main_project_ref`：主业项目锚定引用表，【如果已有项目主数据则不新建，仅缓存必要字段】。  
`cost_project_basic`：项目基本情况表，对应 Table 2，建议字段包括 `main_project_id`、`sub_system_name`、`user_name`、`acquire_method`、`research_unit`、`target_price`、`compete_contract_amount`、`target_cost_amount`、`stage`、`cycle_start`、`cycle_end`、`remark`、`status`。  
`cost_workorder_basic`：工作令基础信息表，对应 Table 3，建议字段包括 `main_project_id`、`workorder_no`、`workorder_name`、`workorder_target_cost`、`stages`、`max_stage`、`sub_system_name`、`product_short_name`、`quantity`、`is_vertical_division`、`remark`、`status`。

## 第一阶段 MVP、主要风险与实施顺序

如果你是第一次接这种项目，我非常明确地建议：**第一阶段不要把“驾驶舱、对比、自动预警、审批流”都背在自己身上。** 第一阶段 MVP 应该以“数据能进、能查、能改、能控权限”为目标，而不是以“所有炫酷页面都上线”为目标。最合理的 MVP 范围是：菜单与路由接入；领域/系列/型号树或简化筛选入口；项目列表页；项目详情页；锚定项目信息读取；Table 2 与 Table 3 的增删改查；保存草稿；基础查询筛选；基础按钮权限；至少一个模板下载与导入能力。对比页、预警看板、自动扫描推送、审批流、版本对比都建议放在第二阶段。这样做的理由很简单：原型虽然都有入口，但公式、审批、推送对象、阈值这些规则还没有在仓库里固化，而 CRUD + 导入是已有参考模块最成熟、最适合 AI 仿照生成的部分。fileciteturn91file0L3-L3 fileciteturn92file0L3-L3 fileciteturn93file0L3-L3 fileciteturn100file0L3-L3 fileciteturn102file0L3-L3 fileciteturn81file0L3-L3

实施顺序我建议这样排。先做**壳子接入**：前端新建成本库目录、菜单、路由、空页面，打通中台权限。再做**列表页**：项目列表查询 + 进入详情。再做**详情页**：把左侧锚定信息 + Table 2 + Table 3 的只读骨架做出来。然后补**保存接口**和**增删改**。接下来加**模板下载和导入**，优先做一个表，跑通批量导入链路。等这几步都稳定了，再考虑预警和驾驶舱。这个顺序的好处是：每一步都能用现有参考模块直接类比，AI 的成功率会高很多。fileciteturn104file0L3-L3 fileciteturn100file0L3-L3 fileciteturn99file0L3-L3 fileciteturn81file0L3-L3

高风险点主要有六个。第一，**主数据边界不清**：领域、系列、型号、主业项目、工作令到底哪些是本模块维护，哪些是外部系统提供，这会直接决定表怎么建。第二，**指标公式不清**：首页的合同金额、到款率、账面金额、目标金额、执行率、超支率到底怎么算，原型只表达了展示意图，没有表达计算规则。第三，**角色与数据权限粒度不清**：是到菜单级、按钮级、字段级，还是到“只看本单位数据”的行级权限。虽然框架已有数据权限能力，但规则本身还需要定义。第四，**审批流是否真要做**：原型提供了审批侧边栏，但如果真的接 BPM，就不是普通 CRUD 难度了。第五，**现有业务模块权限实现不完全统一**：你会看到有些类似模块里 `@PreAuthorize` 是启用的，有些地方又被注释掉了，所以你不能无脑复制任何一个示例；必须自己明确成本库的权限要求。第六，**AI 生成代码容易跑偏版本**：后端是 Java 8 + Spring Boot 2.7，不要让 AI 输出 Java 17 新语法、也不要让它按新一代 Spring Boot 3 的写法来。fileciteturn52file0L3-L3 fileciteturn110file0L3-L3 fileciteturn56file0L3-L3 fileciteturn65file0L3-L3 fileciteturn66file0L3-L3 fileciteturn68file0L3-L3

## 你能不能用 vibe coding 把它做下来

我的答案是：**能，但前提是你把自己定位成“AI 驱动的模块集成人”，而不是“完全不懂后端也能自动交付的独狼工程师”。** 这个项目对你来说最现实的打法，不是让模型“从零发明系统”，而是让模型围绕现有仓库做四件事：读架构、找参考、产文档、仿照开发。你手头最有价值的资产其实不是那套 React 代码，而是“已被业务认可的原型 + 一个成熟中台 + 一堆相似模块”。这三样东西组合起来，正是 vibe coding 最适合发挥的场景。fileciteturn105file0L3-L3 fileciteturn106file0L3-L3 fileciteturn52file0L3-L3

## 还需要确认的关键问题与当前限制

现在最需要你去追问业务和技术同事的，不是“还有没有别的页面”，而是下面这些问题。  
业务侧要确认：领域/系列/型号树的数据源；主业项目锚定信息的数据源；Table 2 和 Table 3 各字段的口径、必填性和单位；首页每个指标的公式；预警阈值和分级；推送对象；审批流要不要真接 BPM；版本对比要不要保留历史。  
技术侧要确认：成本库应挂在哪个业务模块包下；是否已经有项目主数据表；用户/组织/字典/单位关系字段怎么取；是否已有“只看本单位数据”的统一数据权限规则；是否允许先不接 BPM 用业务状态流转替代。
