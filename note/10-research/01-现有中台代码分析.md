# 现有中台代码分析

状态：初稿

## 1. 分析目标

确认成本库 MVP 应复用的数据中台能力、参考模块和代码落点。本阶段只分析现有代码和形成开发依据，不生成业务代码。

## 2. 结论摘要

| 主题 | 结论 |
|---|---|
| 前端技术取舍 | 成本库应在 `costree-frontend` 中按 Vue3/Yudao UI 风格重写。Figma 生成的 React/Vite 项目只作为页面布局、字段、交互状态参考，不建议直接迁入。 |
| 后端模块取舍 | 后端建议新增独立业务模块 `yudao-module-cost`，但要接入根 `pom.xml`、模块 `pom.xml`、启动扫描、菜单权限 SQL 等中台规范【需确认】。 |
| MVP 优先复用能力 | 登录态、动态菜单、按钮权限、租户请求头、请求封装、Excel 导入导出、分页返回、基础数据权限、消息/预警已有能力。 |
| 最接近参考模块 | 前端和后端导入导出优先参考 `finance/baseworkhour`；项目类状态和按钮权限参考 `digital/project`；消息预警参考 `center/messages`、`center/warnconfig`、`center/warnrecord`。 |
| 最大不确定点 | 真实消息推送入口、数据权限字段规则、成本库菜单和权限编码、Excel 模板业务字段、项目基本情况/工作令基础信息字段口径仍需确认。 |

### 3.2 请求封装和登录态

### 3.3 菜单和路由

相关文件：

### 4.6 数据权限

参考文件：

`<backend-root>/yudao-framework/yudao-spring-boot-starter-biz-data-permission/src/main/java/cn/iocoder/yudao/framework/datapermission/core/annotation/DataPermission.java`

已确认：

| 事实 | 影响 |
|---|---|
| `@DataPermission` 可声明在类或方法上 | 成本库可在 Controller/Service 方法或 Mapper 查询链路上接入 |
| 注释说明默认开启数据权限 | 成本库表字段若不匹配规则，可能出现查不到数据或权限失效 |
| `enable=false` 可禁用 | 不建议 MVP 默认禁用，除非排查阶段临时验证 |

需确认：

- 成本库数据权限按部门、项目负责人、填报人、领域/型号归属，还是按系统角色控制。
- 成本库主表是否必须保留 `dept_id`、`user_id`、`creator`、`tenant_id` 等字段来适配现有规则。
- 是否需要新增自定义数据权限规则。

### 4.7 消息和预警

参考模块：

`<backend-root>/yudao-module-center`

已确认文件：

| 能力 | 文件 |
|---|---|
| 消息主表 CRUD | `controller\admin\messages\MessagesController.java` |
| 消息接收人 CRUD / 个人未读消息 | `controller\admin\messagesreceivers\MessagesReceiversController.java` |
| 预警配置 | `controller\admin\warnconfig\WarnConfigController.java` |
| 预警记录 | `controller\admin\warnrecord\WarnRecordController.java` |
| 预警定时任务 | `xxlJob\warnCheck\WarnCheckJob.java` |
| 消息 API | `yudao-module-center-api\src\main\java\cn\iocoder\yudao\module\center\api\CenterMsgApi.java` |

已确认：

- `MessagesReceiversController` 有个人未读消息接口，例如 `getPersonalMsg`、`getPersonalMsgCount`、`setMsgRead`。
- `WarnConfigController` 和 `WarnRecordController` 均有分页、导出等后台管理能力。
- `WarnCheckJob` 使用 `@XxlJob("warnCheckJob")` 和 `@TenantJob`，从预警配置生成/更新预警记录。
- `CenterMsgApi` 暴露了 `sedMsgs(psndocid)`，但命名像 `sendMsgs` 拼写错误，且 `MsgApiImpl` 中存在硬编码作者、接收人、标题、URL 的示例逻辑。

结论：MVP 的“10% 超支预警、全部推送”不建议第一步深度接入 `WarnCheckJob`。更稳妥的路径是：

1. 成本库内部先生成成本预警记录。
2. 复用中心消息表或服务写入消息/接收人。
3. 推送目标临时按“全部用户”或指定测试用户。
4. 等真实消息入口确认后，再接入正式推送链路。

需确认：正式推送是否只要写消息表，还是还要调用外部待办/门户/邮件/短信接口。

## 7. 高风险点

| 风险 | 说明 | 建议 |
|---|---|---|
| 新增后端模块接入失败 | Yudao 多模块需要根 POM、模块 POM、依赖、启动扫描、Mapper 扫描一致 | 先用最小 `cost-biz` 跑通一个只读接口【需确认】 |
| 数据权限字段不匹配 | 默认数据权限可能依赖部门、用户、租户字段 | 成本项目主表先预留 `dept_id`、`owner_user_id`、`tenant_id` 等字段【需确认】 |
| 消息推送入口不清 | `MsgApiImpl` 当前存在硬编码示例，不像最终业务 API | MVP 先写预警记录和消息记录，正式推送入口单独确认 |
| React 原型误用 | React 代码直接迁入会破坏现有 Vue3 工程风格 | 只把 Figma/React 当页面字段和交互蓝本 |
| Excel 模板字段不稳定 | 项目基本情况和工作令基础信息字段未最终确认会导致导入返工 | 先做一个最小模板，字段全部标记版本 |
| 权限编码后改成本高 | 菜单和按钮权限会写入系统表/角色绑定 | 先固定 `cost:*:*` 编码规则再生成 SQL |

## 8. 需要确认的问题

| 对象 | 问题 |
|---|---|
| 业务 | 项目基本情况和工作令基础信息的字段、必填规则、金额单位、精度。 |
| 业务 | “保存草稿”和“提交”后的可编辑范围，以及是否需要退回/撤回。 |
| 业务 | 成本超支 10% 的基准值：预算、目标成本、上期成本还是导入字段。 |
| 业务 | 领域-系列-型号三级树是全局基础数据，还是随项目维护。 |
| 技术 | `yudao-module-cost` 是否允许新增，还是必须放入已有 `finance` / `data` 模块。 |
| 技术 | 成本库数据权限按部门、角色、项目负责人、型号归属中的哪一种生效。 |
| 技术 | 菜单 SQL、权限 SQL、角色绑定由谁维护，是否允许外网测试库先写 mock。 |
| 技术 | 真实消息推送入口：写中心消息表即可，还是要调用门户/待办/即时推送接口。 |
| 技术 | 内网真实数据源字段和外网 MySQL 测试数据的映射方式。 |
