# 05-长期项目文档与工程经验沉淀模式

更新时间：2026-06-12

用途：把成本库项目当前采用的“文档中心 + 状态台账 + 工程经验手册 + 变更追溯”模式沉淀为可复刻方法。后续只要是周期超过一周、涉及多轮需求、多人协作或 AI 辅助开发的项目，都可以按本文初始化和维护。

## 1. 核心理念

长期项目不能只靠聊天记录、临时 prompt 和代码记忆推进。正确做法是把项目事实、当前状态、风险、决策、实现经验和验收方式固定在项目本地文档中心里。

这套模式解决四类问题：

| 问题 | 解决方式 |
|---|---|
| 过几天忘了做到哪 | 用 `PROJECT_STATE.md` 固定当前状态和下一步 |
| 新需求凭感觉开发 | 用 PRD、接口、数据、页面文档先落规格 |
| 踩过的坑重复出现 | 用工程经验手册沉淀推荐做法和反模式 |
| 修改后无法追溯原因 | 用 `DECISIONS.md`、`RISKS.md`、`90-logs` 留痕 |

### 1.1 把文档当成项目操作系统

文档中心不是归档柜，而是每天开发前后都要使用的项目操作系统。

| 层级 | 文件 | 作用 |
|---|---|---|
| 快速恢复层 | `.agent-handoff/` | 给新会话快速知道当前做到哪、下一步做什么 |
| 入口导航层 | `note/README.md` | 告诉后来者先看什么、代码在哪里、专题文档在哪里 |
| 当前状态层 | `PROJECT_STATE.md` | 固定当前目标、已完成、未完成、阻塞和下一步最小任务 |
| 任务执行层 | `PLAN.md` | 固定任务优先级、前置条件、产出范围和验收标准 |
| 风险控制层 | `RISKS.md` | 固定业务、部署、数据口径和工程风险 |
| 决策追溯层 | `DECISIONS.md`、`90-logs/01-决策记录.md` | 固定关键取舍和复核触发条件 |
| 工程经验层 | `00-overview/04-工程经验与开发约束手册.md` | 固定可复用做法、反模式和验收习惯 |
| 过程追溯层 | `90-logs/02-变更日志.md` | 固定每轮变更和验证结果 |

使用原则：

- 开发前用这些文件恢复上下文，而不是依赖上一轮聊天记忆。
- 开发中按文件职责归位更新，而不是把所有内容堆进一个文档。
- 开发后更新状态、计划、风险、变更日志和交接信息，让下一轮能继续。

## 2. 文档中心标准结构

每个长期项目建议先建立 `note/` 或 `docs/`，目录职责固定，不随意新建平行体系。

```text
note/
├── README.md
├── PROJECT_STATE.md
├── PLAN.md
├── DECISIONS.md
├── RISKS.md
├── AGENTS.md
├── 00-overview/
├── 10-research/
├── 20-requirements/
├── 30-data/
├── 40-api/
├── 50-frontend/
├── 60-backend/
├── 70-testing/
├── 80-deployment/
└── 90-logs/
```

| 位置 | 负责内容 |
|---|---|
| `README.md` | 文档中心入口、代码仓库路径、当前阶段、重点阅读、维护规则 |
| `PROJECT_STATE.md` | 当前目标、已完成、未完成、阻塞、关键决策、下一步最小任务 |
| `PLAN.md` | 阶段任务、优先级、前置条件、产出范围、验收标准、状态 |
| `DECISIONS.md` | 关键技术和业务取舍索引 |
| `RISKS.md` | 业务确认项、部署风险、数据口径风险、工程质量风险 |
| `AGENTS.md` | Codex/AI 协作边界、验证要求、文档归位规则 |
| `00-overview/` | 总览、路线图、运行链路、代码阅读地图、工程经验手册 |
| `10-research/` | 现有系统、原型、参考模块、依赖分析 |
| `20-requirements/` | PRD、角色权限、页面拆分、确认问题 |
| `30-data/` | 数据对象、表结构、枚举、SQL、测试数据、源表映射 |
| `40-api/` | 接口清单、字段契约、请求响应、联调用例 |
| `50-frontend/` | 页面迁移计划、页面实现说明、UI 决策、前端验证 |
| `60-backend/` | 后端模块设计、Controller/Service/Mapper 清单、实现记录 |
| `70-testing/` | 测试计划、验收清单、回归用例 |
| `80-deployment/` | 环境账号指引、内外网迁移、部署手册、配置核对 |
| `90-logs/` | 决策记录、变更日志、过程记录 |

## 3. 项目启动流程

新项目开始时，先不要直接写代码。按以下顺序建立依据：

1. 建 `note/` 或 `docs/` 文档中心。
2. 写 `README.md`：项目目标、代码仓库路径、目录职责、维护规则。
3. 写 `10-research`：现有代码、原型、参考模块和可复用能力。
4. 写 `20-requirements`：MVP PRD、页面清单、角色权限和确认问题。
5. 写 `30-data`：核心数据对象、表结构、枚举、测试数据方案。
6. 写 `40-api`：接口清单和字段契约。
7. 写 `PLAN.md`：第一阶段执行清单和验收标准。
8. 写 `RISKS.md`：业务、部署、数据、工程风险先入账。
9. 写 `AGENTS.md`：约束后续 AI 不乱改、不跳过验证、不凭空开发。

启动阶段的验收标准：

- 文档中心能回答“做什么、怎么做、哪里改、怎么验收”。
- 不确定事项都有 `【需确认】`，并进入风险或确认问题清单。
- 后续代码生成有参考模块、接口契约和数据模型，不依赖临场发挥。

## 4. 每轮开发闭环

每一轮需求或功能都按同一个闭环走。

| 阶段 | 动作 | 产物 |
|---|---|---|
| 新需求进入 | 写清背景、角色、页面、数据源、权限、数据量、验收 | `20-requirements`、`RISKS.md` |
| 开发前 | 读 README、PROJECT_STATE、相关专题文档、工程经验手册 | 明确范围和禁忌 |
| 开发中 | 小步修改，按现有风格复用代码模式 | 前端、后端、SQL、接口文档同步 |
| 验收时 | 跑类型检查、ESLint、后端编译、接口和页面验证 | `70-testing` 或变更日志 |
| 开发后 | 更新状态、计划、风险、决策、变更日志 | `PROJECT_STATE.md`、`PLAN.md`、`RISKS.md`、`90-logs` |
| 复盘沉淀 | 把踩坑和可复用模式写成规则 | 工程经验手册 |

### 4.1 每轮开发的固定节奏

每次开工先做 5 分钟恢复：

1. 读 `.agent-handoff/CURRENT.md`。
2. 读 `note/README.md`、`PROJECT_STATE.md`、`PLAN.md`。
3. 读本轮相关专题文档，例如 `30-data`、`40-api`、`50-frontend`、`60-backend`。
4. 查 `00-overview/04-工程经验与开发约束手册.md`，确认是否已有可复用模式或反模式。

每次新需求先规格化：

- 谁使用。
- 看什么页面。
- 能做什么操作。
- 数据从哪里来。
- 是否分页，预估数据量多大。
- 是否涉及权限、租户、导入、导出、预警、审批。
- 不确定项统一标记 `【需确认】`，进入 `RISKS.md` 或需求确认文档。

每次开发中做最小同步：

- 改接口，同步 `40-api`。
- 改表结构，同步 `30-data` 和 `80-deployment`。
- 改页面，同步 `50-frontend`。
- 改后端实现，同步 `60-backend`。
- 发现风险，同步 `RISKS.md`。
- 做关键取舍，同步 `DECISIONS.md`。
- 踩坑形成规则，同步工程经验手册。

每次收尾固定做 10 分钟：

1. 更新 `PROJECT_STATE.md`：当前目标、已完成、未完成、阻塞、下一步最小任务。
2. 更新 `PLAN.md`：任务状态和验收结果。
3. 更新 `90-logs/02-变更日志.md`：本轮变更摘要和验证情况。
4. 更新 `.agent-handoff`：让新对话能接管。
5. 明确本轮跑过哪些验证，没跑哪些验证。

必须养成的习惯：

- 开发前先查有没有已有模式。
- 新需求先落规格，再让 AI 或开发者写代码。
- 改接口就改接口文档。
- 改 SQL 就改数据文档和部署文档。
- 改页面行为就改前端说明。
- 遇到风险就进 `RISKS.md`，不要只留在聊天记录。
- 形成关键取舍就进 `DECISIONS.md`。

## 5. 工程经验沉淀方式

经验不是复盘小作文，必须写成可以执行的规则。

推荐格式：

| 字段 | 写法 |
|---|---|
| 编号 | 稳定编号，例如 `BE-001`、`FE-002`、`ANTI-001` |
| 场景 | 什么情况下适用 |
| 推荐做法 | 后续默认怎么做 |
| 禁止/慎用 | 哪些写法已经证明有风险 |
| 参考文件或函数 | 去哪里看现成实现 |
| 验收方式 | 怎么证明没有踩坑 |
| 状态 | 已验证、需验证、已废弃 |

适合沉淀的经验：

- 分页和性能规则，例如禁止全量查再手动分页。
- 登录态、租户、权限规则，例如默认复用真实中台登录态。
- 导入导出规则，例如同步导出设置最大行数。
- 数据聚合规则，例如只聚合当前页工作令。
- 接口字段契约规则，例如分页响应统一使用 `PageResult`。
- 新需求撰写模板，例如必须写清角色、数据源、权限、验收。
- 反模式清单，例如 mock login 覆盖真实用户、假数据混入真实页面。

不适合写进工程经验手册的内容：

- 单个接口的完整字段表，应放 `40-api`。
- 单张表的字段说明，应放 `30-data`。
- 单个页面的 UI 细节，应放 `50-frontend`。
- 一次具体提交的过程，应放 `90-logs/02-变更日志.md`。
- 账号密码，应集中放部署敏感信息文档。

## 7. AI 协作方式

AI 最适合做“有依据的加速”，不适合在缺少规格时自由发挥。

建议 prompt 顺序：

1. “先阅读文档中心和现有代码，不要写代码，只分析应该改哪里。”
2. “基于现有参考模块，输出计划和接口/数据/页面影响，不确定处标记【需确认】。”
3. “请按计划小步实现，不改无关文件。”
4. “实现后跑指定验证，并更新对应文档。”
5. “把本轮踩坑和可复用经验写入工程经验手册。”

AI 协作约束：

- 不让 AI 直接跳过需求文档写代码。
- 不让 AI 新建平行目录或平行架构。
- 不让 AI 修改无关代码做顺手重构。
- 不让 AI 把本地日志、个人配置、敏感信息纳入提交。
- 不让 AI 用“页面能看”替代类型检查、后端编译和接口验证。

## 8. 维护节奏

| 时机 | 必做动作 |
|---|---|
| 每次开始新功能 | 查 `PROJECT_STATE.md`、`PLAN.md`、工程经验手册 |
| 每次需求变化 | 更新 PRD、接口、数据或页面文档中的对应位置 |
| 每次发现风险 | 更新 `RISKS.md` |
| 每次做关键取舍 | 更新 `DECISIONS.md` 或 `90-logs/01-决策记录.md` |
| 每次完成阶段任务 | 更新 `PROJECT_STATE.md` 和 `PLAN.md` |
| 每次踩坑修复 | 更新工程经验手册和变更日志 |
| 每次准备内网或生产部署 | 检查 `80-deployment` 和敏感信息文档 |

### 8.1 周期性文档巡检

每周做一次 30 分钟文档巡检：

- 看 `PROJECT_STATE.md` 是否仍能反映当前项目状态。
- 看 `PLAN.md` 是否还有无效任务、重复任务或状态错误。
- 看 `RISKS.md` 是否有长期未处理的 `【需确认】` 项。
- 看 `DECISIONS.md` 是否漏掉近期关键取舍。
- 看工程经验手册是否沉淀了最近踩坑。
- 看 README 当前重点阅读是否仍然准确。

每个阶段结束做一次复盘：

- 把真正可复用的经验写入工程经验手册。
- 把关键取舍补到决策索引。
- 把已废弃方案标记为“已废弃”或移入历史说明。
- 清理重复描述，保留一个事实的主位置，其他地方只做链接引用。

## 9. 判断文档是否有效

有效的文档中心应该能让后来者快速回答：

- 当前项目目标是什么？
- 现在做到哪一步？
- 下一步最小任务是什么？
- 哪些地方不能乱改？
- 哪些风险还没确认？
- 新增需求应该先补哪些信息？
- 前端、后端、SQL、接口分别改哪里？
- 改完应该跑哪些验证？
- 已经踩过哪些坑，以后怎么避免？

如果这些问题回答不了，说明文档中心需要补齐；如果回答得到但内容太长找不到，说明文档需要拆分和建立索引。

## 11. 可复用 Prompt

### 开工恢复

```text
请接管 <costree-root> 项目。先不要写代码。
请读取 .agent-handoff、note/README.md、PROJECT_STATE.md、PLAN.md、RISKS.md、AGENTS.md 和工程经验手册。
然后输出当前目标、已完成、未完成、阻塞、下一步最小任务和本轮开发约束。
```

### 新需求规格化

```text
请先把这个需求整理成可开发规格，不要写代码。
必须包含：角色、页面、数据源、权限、分页/性能、接口、表结构影响、验收标准、【需确认】事项。
```

### 收尾沉淀

```text
请收尾本轮工作：更新 PROJECT_STATE.md、PLAN.md、RISKS.md、DECISIONS.md、90-logs/02-变更日志.md 和 .agent-handoff。
把本轮新增经验写入工程经验手册。
```

### 文档健康检查

```text
请检查 <costree-root>/note 文档中心是否过期、重复、缺入口或缺验收标准。
只输出需要修的地方和建议修改，不要直接改文件。
```

## 12. 保持文档活力的判断标准

文档需要持续服务开发，而不是增加维护负担。后续按以下标准判断是否要更新：

- 能影响下一轮开发决策的，必须更新。
- 能避免重复踩坑的，必须沉淀。
- 只是一次性过程细节的，放变更日志，不扩散到多个文档。
- 已经过期但可能误导后续开发的，要标记“已废弃”或移入历史。
- 涉及账号、密码、Token、个人配置的，不进入 README、交接文档和外发文档。
