# 成本树 20261009 完整离线包

本包更新成本后端和现有中台前端，包含经典首页、历史单位归类、工作令明细交互及账面筛选范围修复。后端从本次已推送的固定提交在 Linux 服务器构建并下载；前端经用户确认改在 Windows 本机纯构建，没有启动本地服务。具体提交、构建环境和哈希见 `RELEASE-INFO.json`。

## 先分清两件事

- **升级应用**：使用 `01-database` 核对结构，再部署 `03-app`。没有为本轮页面和筛选修复新增业务表字段。
- **改日常数据同步**：使用 `05-workflow/README.md`，只清本批中间表，按字段白名单更新业务表，不再删除重建业务数据。同步辅助表单独初始化，不要把初始化或业务升级放进每日任务。

## 应用升级步骤

1. 解压整包。Windows 在包根目录执行 `powershell -File .\verify-package.ps1`；Linux 执行 `sha256sum -c SHA256SUMS.txt`。校验失败时不要安装。
2. 备份旧 cost JAR、整份前端目录、外置配置、成本库，以及当前云鲸工作流和节点 SQL。暂停旧同步调度和业务写入，按现场维护窗口更新。
3. 用 `01-database/00-identify-schema.sql` 确认 cost 实际数据库、schema 和租户，数据库名不等于 schema。离线 `01-database/sql-parameters.html` 可生成实际参数的升级副本。
4. 已完成旧版全部升级的库，先执行 `03-verify-structure.sql`，通过后通常直接换应用。结构不完整时执行 `01-full-upgrade.sql` 后再次核验；备用 `02-backup-create-missing-tables.sql` **仅建缺表**，不能给已有表补缺列。不要盲目依次执行所有 SQL，不要清 migration 表。
5. 只替换 `03-app/cost-server.jar`，保留现场端口、数据库、Redis、Nacos、租户和密钥。原启动方式及外置配置继续使用，详见 `03-app/README.md`。
6. 将 `03-app/dist-prod.zip` 解压到新的静态目录，检查根目录有 `index.html`，再整体切换。不要覆盖混合旧 assets。API 为同源 `/admin-api`，沿用现场代理。
7. 强刷并重新登录，验收经典首页项目数/金额、四领域、单位分类、八项明细、筛选及六类身份权限。首发固定经典页，3D 舱和平台舱入口隐藏。
8. 应用核验完成后，再按 `05-workflow` 在工作流副本中替换同步节点；试跑与重复运行对账通过后才恢复调度。不要把旧“删除业务表”节点接回新流程。

## 本包关键变化

- 首页增加授权范围内正式领域的去重项目数，保留中间四个六角图，两侧使用可穿透的八项金额条形图；正、负、零金额均保留。
- 同名历史核算编码归属一致时不再误判冲突，真实冲突继续提示核对；不按名字对账面记录盲目去重或累计。
- 修复下拉重复展开请求，以及有账面但项目主表未关联时基础下拉消失的问题。项目、单位、工作令根据可查询账面返回；领域、型号没有真实归属时仍为空。
- 保留之前的 17 成本实体程序生成主键、授权版本、明细打开竞态等修复；不更改收益率公式。
- 日常同步改为用户确认的“全量快照＋差异更新”，不是依赖更新时间水位的增量抽取。人工填报与源快照分开管理，保护原业务 ID、手填字段和流程状态。

## 脚本与数据边界

`01-database` 完整与备用结构脚本覆盖 20 张成本表，包含 `cost_user_role`、`cost_user_role_action`、`cost_auth_user_lock` 和三类授权范围表。原应用升级 SQL 沿用已验证版本；工作流辅助结构和模块在 `05-workflow` 单独交付。

源表名、源字段、源记录稳定键及单位映射需要在内网按映射清单修改；未适配的模板不得直接上线。首次运行失败必须停止，不能跳过校验节点。已被旧流程清掉的填报内容不会被新流程自动恢复，需要从备份恢复或由业务重新填报。

本包不部署 system、Data、SQLBot，不修改中台 DM 库；完整前端中的其他入口沿用原权限。不要以本包替换其他服务 JAR。

## 验收与回退

构建、回归和包完整性证据在 `04-evidence`，实际结果见 `RELEASE-INFO.json`；历史 PG 测试、嵌入式 SQL 测试、服务器构建都不等于真实 DWS 或云鲸 2.2.1 已现场通过。

现场至少确认：六类账号和撤权、八项明细连续点击、筛选后的账面明细金额、真实项目数、同名历史编码归类、填报保存后同步两次不丢失、异常批次整体回滚。性能问题不得通过删除权限过滤或扩大账面口径绕过。

回退时先停写和停同步，再按备份恢复应用及确需恢复的数据。旧 JAR 对本地授权/撤销的兼容性须复核；同步失败不要恢复旧破坏性删除任务。保留旧包和旧配置，禁止先删除唯一备份。
